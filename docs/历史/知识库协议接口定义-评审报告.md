## 一、评审摘要

该协议定义了一套面向 AI Agent 自动化硬件编程的"AI 原生知识库"规范，由文档知识库（DKB）、A-HAL 代码知识库、社区资源知识库（CRKB）三部分组成，并提供统一的 Python 查询接口（精确查表 + 向量检索 + hybrid_search 联合检索）。

**核心评价**：

- **真创新**：A-HAL + `ahal_api.json` 的 AI 原生 API 契约（含 preconditions/side_effects/resource_conflict）填补了业界空白，arxiv 2501.12420 论文证实裸 LLM 生成嵌入式代码成功率仅 36.7%，A-HAL 约束 AI 边界的设计具备实证支撑。
- **重复造轮子**：`registers.json` 实质是"用 JSON 重发明 CMSIS-SVD"，通篇未提 SVD/CMSIS，放弃了 ARM 生态十余年积累的厂商库、调试器、svd2rust 生成器。
- **思路对但欠成熟**：`hybrid_search` 多源结果仅"字段拼接"未做 rank fusion，未复用 LangChain `EnsembleRetriever` / LlamaIndex 成熟组件。

**P0 阻塞性问题 2 项**（SVD 缺失、rank fusion 缺失）；**P1 工程化缺口 4 项**；**P2 清理项 4 项**。详见第七章。

## 四、价值评估（合理且领先的设计）

### 4.1【业界空白】A-HAL 契约元数据

`ahal_api.json` 中每个 API 条目附带 `preconditions / postconditions / side_effects / resource_conflict / performance / errors` 六类机器可消费元数据。

**业界对照**：
- TinyML 论文（arxiv 2501.12420）使用 LLM 做嵌入式代码生成，**未定义任何 HAL**，仅靠 prompt 注入硬件上下文 + 最多 5 次重试，Sketch 生成成功率仅 36.7%。
- TF `REGISTER_OP` 有 shape inference / PyTorch 有 autograd 元数据，但均面向"算子调度"，**无面向 AI 代码生成场景的契约元数据**。
- 业界无面向 AI Agent 的硬件抽象层规范 → 该协议 A-HAL 是真正的领域创新。

**价值**：通过契约元数据约束 AI 生成代码的行为边界（必须满足前置条件、必须知道副作用、必须规避资源冲突），从根本上提升嵌入式代码生成的可验证性。这一设计应**保留并加强**。

### 4.2【精准对症】三库分层 + 精确/语义分离存储

文档知识库用 JSON Schema 严格定义（registers/pins/clock 等表格类信息精确查表），社区资源用 JSONL + 向量化（问答类信息语义检索）。

**业界对照**：
- 业界主流 RAG 倾向"全量向量化"，但嵌入式手册中寄存器表、引脚复用表等**结构化表格向量化后召回质量极差**（向量相似度无法表达"地址 0x94 对应 P0M0"这种精确映射）。
- LlamaIndex 虽支持 `SQLRetriever + VectorRetriever` 组合，但需用户自行拆分；该协议**在 schema 层就完成了分离**，工程化更彻底。

**价值**：精准应对嵌入式领域知识形态的天然差异。这是该协议第二个应当保留的领先设计。

### 4.3【工程化意识】`consistency_check` 跨库门禁

```bash
python -m mcu_agent.kb.consistency_check stc8h8k64u
```

校验 A-HAL API 引用的寄存器是否在 `registers.json` 中存在，识别不一致项必须修复或标注 `known_gap`。

**价值**：在知识库构建阶段就引入跨库一致性门禁，避免 AI 生成代码时引用不存在的寄存器。这一门禁机制是工程化意识的体现，应保留。

### 4.4【细节到位】结构化 frontmatter 与来源追溯

`peripherals/*.md` 与 `patterns/*.md` 使用 YAML frontmatter 标注 `peripheral / chip / ahal_requires / tags`；每条记录的 `source` 字段含 `document / version / extracted_at / method`。

**价值**：满足"来源可追溯"的审计需求，对长期维护与增量更新友好。

## 五、问题诊断（严格批判式）

### 5.1【严重·P0】未引用 CMSIS-SVD，重复造轮子且丢失生态

**问题**：协议通篇 746 行**无 "SVD" 或 "CMSIS" 字样**。`registers.json` 自定义的 `name / address / reset_value / access / fields / values` 字段集，与 CMSIS-SVD 的 `register / addressOffset / resetValue / access / fields / enumeratedValues` 几乎一一对应——**实质是用 JSON 重新发明了 SVD**。

**业界对照**：
- **CMSIS-SVD** 是 ARM 事实标准，层级 `Device → CPU + Peripherals → Registers → Fields → EnumeratedValues`，含 `description / resetValue / access / dimensions / derivedFrom（继承） / vendorExtensions（厂商扩展）`。
- **ST 原厂 / Nordic / NXP / Nuvoton** 等均发布官方 SVD 文件，调试器（OpenOCD/pyOCD）、SVDConv、svd2rust 等工具链直接消费。
- **svd2rust** 从 SVD 自动生成类型安全的 Peripheral Access Crate（PAC），演进出 svdtools/chiptool/metapac 等成熟工具链。

**损失**：
1. **放弃调试器生态**：OpenOCD/pyOCD 可直接读取 SVD 显示寄存器值，自造 JSON 无法复用。
2. **放弃代码生成生态**：svd2rust 可从 SVD 生成类型安全的 Rust PAC；自造 JSON 无生成器，仅服务于 LLM 查表。
3. **放弃厂商生态对接**：未来若扩展到 STM32F103（Cortex-M），ST 原厂 SVD 可直接导入；自造 JSON 则需手工转写或写适配器，重复劳动。
4. **schema 演进风险**：SVD 由 ARM 维护，历经多年演进；自造 schema 需自行承担所有演进成本。

**反方观点的回应**：STC8H 是 8051 架构（非 ARM Cortex-M），可能有人认为 SVD 不适用。但 SVD 的 `vendorExtensions` 机制就是为非标扩展设计的；且 SVD 的 `CPU` 元素并不强制要求 Cortex-M，可填 `Other`。详见第六章 SVD 映射方案。

### 5.2【严重·P0】hybrid_search 缺失 rank fusion，多源结果仅字段拼接

**问题**：`hybrid_search` 返回 `HybridResult` 数据类，其中 `registers / apis / patterns / docs / community` 五个字段分别承载不同来源的结果，但**无统一排序、无权重融合、无去重**。

```python
@dataclass
class HybridResult:
    registers: list[RegisterDef]     # 精确查表命中（无 score）
    apis: list[AHALAPIDef]           # A-HAL API 命中（无 score）
    patterns: list[SearchHit]        # 语义匹配（有 score）
    docs: list[SearchHit]            # 语义匹配（有 score）
    community: list[SearchHit]       # 语义匹配（有 score）
```

**业界对照**：
- **LangChain `EnsembleRetriever`**：合并 BM25（稀疏）+ 向量（密集），可配权重，使用 **RRF（Reciprocal Rank Fusion）** 算法融合排序。
- **LlamaIndex Hybrid**：支持 keyword AND/OR vector 混合，并提供 `FusionRetriever` 做排序融合。
- 业界成熟范式：**稀疏检索 + 密集检索 + 排序融合**。

**损失**：
1. **多源结果未真正融合**：精确查表命中（无 score）与语义匹配（有 score）无法统一排序，LLM 收到的上下文中信息密度无优化。
2. **重复信息未去重**：`registers` 精确命中 `SCON`，`docs` 语义命中 UART 文档（其中也描述 SCON），`community` 命中 UART 问答（同样涉及 SCON），三处重复未去重。
3. **上下文 token 浪费**：未融合排序的结果直接灌入 LLM prompt，可能浪费 token 在低价值信息上。

**修复方向**：实现 RRF 融合，或直接复用 LangChain `EnsembleRetriever`。详见 7.1 P0-2。

### 5.3【中·P1】ahal_api.json 手写+事后 lint，无声明式→生成链路

**问题**：`ahal_api.json` 是手工维护的 JSON 文件，`consistency_check` 是事后兜底校验。

**业界对照**：
- **TensorFlow**：`REGISTER_OP` 宏在 C++ 中声明式注册 op（name/attrs/inputs/outputs/shape inference），由框架统一调度与校验。
- **PyTorch**：`native_functions.yaml` 声明 ATen 算子签名，代码生成器产出 Python/C++ 绑定。
- **MLIR**：TableGen/ODS 声明 operation schema。
- 共性：**"声明式 source of truth → 生成 + 校验"**，非手写 JSON + 事后 lint。

**损失**：
1. A-HAL 头文件（`code/ahal/stc8h8k64u/gpio.h`）与 `ahal_api.json` 是**两份独立维护的真相源**，必然失同步。
2. 修改 A-HAL 函数签名后，需手工同步更新 JSON；遗漏则触发 `consistency_check` 失败，但失败时已是事后。

**修复方向**：以 A-HAL 头文件为单一真相源，用 Doxygen 注释 + clang AST 提取自动生成 `ahal_api.json`。详见 7.2 P1-1。

### 5.4【中·P1】自造 JSON Schema 私有 URL，与 JSON Schema draft/OpenAPI 生态断裂

**问题**：

```jsonc
"$schema": "https://mcu-agent.io/schemas/registers-v1.json"
```

`mcu-agent.io` 是**未注册的私有域**，该 URL 不可解析，无任何 schema 文档。`ahal_api-v1.json` 同样问题。

**业界对照**：
- **JSON Schema 2020-12 draft**：标准化 schema 描述语言，有官方验证器（ajv/python-jsonschema）。
- **OpenAPI 3.1**：REST API 描述标准，与 JSON Schema 完全兼容；gRPC-Gateway 可从 .proto 自动生成 OpenAPI。
- **Protobuf**：强类型 IDL，`protoc` 生成多语言 stub，字段级兼容性规则（wire compatibility）。

**损失**：
1. 无法使用标准 JSON Schema 验证器（需自研 validator）。
2. 无法对接 OpenAPI 生态（Swagger UI、代码生成器、mock server）。
3. 版本演进无规范：`version_history` 是手工 JSON 列表，弱于 Protobuf 的字段级兼容性规则。

### 5.5【轻·P2】sfr_groups 与 peripheral 字段冗余

**问题**：`registers.json` 中每个寄存器已有 `peripheral` 字段：

```jsonc
{ "name": "P0M0", "peripheral": "GPIO", ... }
```

同时 `sfr_groups` 又按 peripheral 分组列出寄存器名：

```jsonc
"sfr_groups": { "GPIO": ["P0", "P0M0", "P0M1", ...] }
```

两者描述同一信息，必然失同步。

**修复方向**：移除 `sfr_groups`，`query_registers_by_peripheral` 改为对 `registers` 数组按 `peripheral` 字段过滤。

### 5.6【轻·P2】version_history 手工 JSON 列表，弱于 git tag+CHANGELOG

**问题**：

```jsonc
"version_history": [
  {"version": "1.0.0", "date": "2026-07-07", "changes": "...", "compatibility": "..."},
  {"version": "1.1.0", "date": "TBD", ...}
]
```

`date: "TBD"` 表明该字段需手工维护，且与 git 提交历史重复。

**修复方向**：改用 `git tag v1.0.0` + `CHANGELOG.md` 标准实践，JSON 中仅保留当前 `ahal_version` 字段。

### 5.7【轻·P2】meta.json.completeness 百分比无校验来源，易腐化

**问题**：

```jsonc
"completeness": {
  "registers": "70%",
  "peripherals_text": "50%",
  "pins": "100%",
  "clock": "100%"
}
```

手工填写的百分比，无校验来源，长期会与实际状态偏离。

**修复方向**：CI 自动统计——`registers` 覆盖率 = `registers.json` 中已定义 SFR 数 / 官方数据手册 SFR 总数。

### 5.8【中·P1】pins.json 的 register_config 字符串引用无 schema 级交叉校验

**问题**：

```jsonc
"register_config": {
  "P1M0.P10": "1",
  "P1M1.P10": "1",
  "ADC_CONTR.CHS": "111",
  "P_SW2.S4_S": "0"
}
```

`"P1M0.P10"` 是字符串形式的"寄存器名.字段名"引用，**schema 层无法校验**该引用是否在 `registers.json` 中存在、`.P10` 是否是 `P1M0` 的合法字段、`"111"` 是否匹配 `CHS` 字段的 bit 宽度。

**损失**：手工录入错误（如把 `P1M0.P10` 写成 `P1M0.P1O`）只能在运行时暴露，无法在 schema 校验阶段拦截。

**修复方向**：改用强类型引用：

```jsonc
"register_config": [
  {"register": "P1M0", "field": "P10", "value": "1"},
  {"register": "ADC_CONTR", "field": "CHS", "value": "111"}
]
```

并在 schema 中用 `$ref` 引用 `registers.json` 的字段定义，实现编译期交叉校验。

### 5.9【中·P1】缺少错误模型（errors 字段仅描述，无错误码/异常分级）

**问题**：

```jsonc
"errors": [
  "若 pin 超出有效范围，无操作（无运行时检查）"
]
```

`errors` 是字符串列表，仅描述性文字，无错误码、无异常分级、无 AI 决策提示。

**损失**：AI Agent 生成代码时，无法基于错误码做决策（如"该错误可忽略" vs "该错误必须处理"）。`preconditions` 已有结构化，但 `errors` 退化为字符串，前后不一致。

**修复方向**：

```jsonc
"errors": [
  {
    "code": "AHAL_E_PIN_OUT_OF_RANGE",
    "severity": "warning",
    "behavior": "no_op",
    "ai_hint": "调用方应在调用前校验 pin 范围，运行时不检查以节省 cycles"
  }
]
```

### 5.10【轻·P2】forum_qa.jsonl 的 verified 字段无验证流程定义

**问题**：

```jsonc
"verified": true
```

布尔字段，但**未定义何为"已验证"**——是作者自述？社区点赞？还是有人在指定硬件上复现？

**修复方向**：改为结构化：

```jsonc
"verification": {
  "status": "verified | unverified | disputed",
  "method": "reproduced_on_hw | community_upvotes | author_claim",
  "evidence_url": "https://..."
}
```

## 六、STC8H SVD 映射方案（针对 8051 架构的具体方案）

### 6.1 STC8H 是否有官方 SVD？

**否**。STC8H 是 8051 增强型架构（非 ARM Cortex-M），STC 官方未发布 SVD 文件。SVD 标准本身面向 Cortex-M，但**格式上可扩展**到其他架构（见 6.2）。

### 6.2 CMSIS-SVD 对 8051 架构的扩展性分析

CMSIS-SVD 的 `vendorExtensions` 元素是为非标扩展设计的逃生通道。关键观察：

| SVD 元素 | 8051 适配性 | 处理方式 |
|----------|-------------|----------|
| `<cpu>` | 不匹配（8051 非 Cortex-M） | 填 `<cpu name="8051" revision="r1p0" endian="little"/>`，或用 `vendorExtensions` 标注 |
| `<addressOffset>` | 适配（SFR 有明确地址） | 直接用 SFR 地址，`baseAddress` 设为 0x80（SFR 区起点） |
| `<size>` | 适配（8051 SFR 为 8 位） | 填 8 |
| `<access>` | 适配 | 直接用 read-write/read-only 等 |
| `<resetValue>` | 适配 | 直接用数据手册值 |
| `<fields>` + `<enumeratedValues>` | 完全适配 | 位寻址区可直接表达 |
| **位寻址区**（0x20-0x2F 的位地址 0x00-0x7F） | **不直接适配** | 用 `vendorExtensions` 表达 `bit_addressable="true"` |
| **bank switching**（8051 ROM/RAM bank） | **不直接适配** | 用 `vendorExtensions` 表达 `bank` 属性 |
| **`access_sequence`**（如 STC 的 TA 解锁序列） | **不直接适配** | 用 `vendorExtensions` 表达 `unlock_sequence` |

**结论**：SVD 的核心元素（register/field/enum）完全能描述 STC8H 寄存器，8051 特有概念通过 `vendorExtensions` 承载。**不引用 SVD 没有技术理由，只有"未调研"的可能**。

### 6.3 推荐方案：定义 STC8H SVD Profile + 双向映射

#### 6.3.1 registers.json ↔ SVD 字段映射表

| `registers.json` 字段 | SVD XML 元素 | 说明 |
|----------------------|--------------|------|
| `name` | `<register>/<name>` | 直接映射 |
| `address` | `<register>/<addressOffset>` | 配合 `<peripheral>/<baseAddress>` |
| `description` | `<register>/<description>` | 直接映射 |
| `reset_value` | `<register>/<resetValue>` | 直接映射 |
| `access` | `<register>/<access>` | `R/W` → `read-write`，`R only` → `read-only` |
| `peripheral` | 所在 `<peripheral>/<name>` | 通过外设分组表达 |
| `fields[].name` | `<field>/<name>` | 直接映射 |
| `fields[].bits` | `<field>/<bitRange>` | `[3,2]` → `[3:2]` |
| `fields[].values` | `<enumeratedValues>` | 直接映射 |
| `special` | `<vendorExtensions>/<stc:special>` | 8051 特有 |
| `access_sequence` | `<vendorExtensions>/<stc:unlockSequence>` | STC TA 解锁序列 |
| `notes[]` | `<register>/<description>` 末尾或 `<vendorExtensions>` | 文本说明 |

#### 6.3.2 SVD 片段示例（STC8H GPIO P0M0）

```xml
<peripheral>
  <name>GPIO</name>
  <description>通用输入输出端口</description>
  <baseAddress>0x80</baseAddress>
  <groupName>GPIO</groupName>
  <registers>
    <register>
      <name>P0M0</name>
      <description>P0 端口模式寄存器 0</description>
      <addressOffset>0x14</addressOffset>  <!-- 0x94 - 0x80 -->
      <size>8</size>
      <access>read-write</access>
      <resetValue>0x00</resetValue>
      <fields>
        <field>
          <name>P00</name>
          <description>P0.0 模式控制 bit0</description>
          <bitRange>[0:0]</bitRange>
          <enumeratedValues>
            <enumeratedValue><name>BIDIR</name><description>准双向口</description><value>0</value></enumeratedValue>
            <enumeratedValue><name>PUSHPULL</name><description>推挽输出</description><value>1</value></enumeratedValue>
          </enumeratedValues>
        </field>
      </fields>
      <vendorExtensions>
        <stc:notes>复位后默认为准双向口模式</stc:notes>
      </vendorExtensions>
    </register>
  </registers>
</peripheral>
```

#### 6.3.3 生成器选择

- **svd2rust**：默认面向 ARM，对 8051 支持有限（8051 无 NVIC/SysTick 等 Cortex-M 元素）。可尝试 `--target=none` 跳过架构特定生成，仅产出 PAC 类型定义。
- **自研 `stc-svdconv`**：Python 工具，从 SVD 解析生成 SDCC BSP 头文件（`__sfr __at(0x94) P0M0;`）+ `registers.json`（供 LLM 查表）。**推荐方案**：SVD 作为单一真相源，同时生成 SDCC 头文件和 LLM 友好的 JSON 视图。

### 6.4 渐进迁移路径

**阶段 A**（不破坏现有 JSON）：
- 在 `tools/` 下新增 `svd_exporter.py`，将 `registers.json` 导出为 `registers.svd`。
- 验证导出的 SVD 能被 SVDConv 或调试器读取。

**阶段 B**（SVD 成为真相源）：
- 反转方向：以 SVD 为单一真相源，`registers.json` 由 `stc-svdconv` 自动生成。
- `registers.json` 保留 LLM 友好的扁平结构，SVD 保留层级结构与生态对接能力。

**阶段 C**（生态打通）：
- STM32F103 扩展时，直接导入 ST 官方 SVD，无需手工录入。
- 评估 svd2rust 生成 Rust PAC 的可行性（若未来扩展 Rust A-HAL）。

## 七、改进优先级排序（P0/P1/P2 详细分级）

### 7.1 P0 级（阻塞性问题，影响协议根本价值）

| ID | 问题 | 影响 | 修复方向 | 工作量 |
|----|------|------|---------|--------|
| **P0-1** | 未引用 CMSIS-SVD，registers.json 重复造轮子 | 放弃调试器/生成器/厂商库生态；未来 STM32 扩展需重复录入 | 见第六章 SVD 映射方案：先建导出层，再反转真相源 | 中（1-2 周） |
| **P0-2** | hybrid_search 缺失 rank fusion | 多源结果未融合排序，token 浪费，LLM 上下文信息密度低 | 实现 RRF 算法，或复用 LangChain `EnsembleRetriever`；统一为 `list[ScoredHit]` 替代 `HybridResult` 多字段 | 小（2-3 天） |

**P0-2 详细修复方案**：

```python
@dataclass
class ScoredHit:
    content: str
    source: str          # doc_kb | ahal_kb | community_kb
    score: float         # RRF 融合后的统一分数
    metadata: dict
    hit_type: str        # register | api | pattern | doc | community

def hybrid_search(self, chip: str, task: str) -> list[ScoredHit]:
    """RRF 融合：score = Σ 1/(k + rank_i)，k 通常取 60"""
    results = []
    # 精确查表命中（rank=1，无向量分数）
    for r in self.query_registers_by_peripheral(chip, parsed_peripheral):
        results.append(ScoredHit(..., score=1.0, hit_type="register"))
    # 向量检索命中
    results.extend(self.search_docs(chip, task))
    results.extend(self.search_patterns(chip, task))
    results.extend(self.search_community(chip, task))
    # RRF 融合
    return rrf_fuse(results, k=60)
```

### 7.2 P1 级（工程化缺口，影响可演进性）

| ID | 问题 | 影响 | 修复方向 | 工作量 |
|----|------|------|---------|--------|
| **P1-1** | ahal_api.json 手写+事后 lint | A-HAL 头文件与 JSON 双真相源必然失同步 | 以头文件为真相源，用 Doxygen+clang AST 自动提取生成 JSON | 中（1 周） |
| **P1-2** | 自造私有 $schema URL | 无法用标准验证器，无法对接 OpenAPI 生态 | 改用 `https://json-schema.org/draft/2020-12/schema`，或迁移到 OpenAPI 3.1 | 小（2 天） |
| **P1-3** | 缺少错误模型 | AI 无法基于错误码决策，errors 与 preconditions 风格不一致 | errors 改为结构化 `{code, severity, behavior, ai_hint}` | 小（2 天） |
| **P1-4** | pins.json register_config 字符串引用无交叉校验 | 手工录入错误只能运行时暴露 | 改为 `{register, field, value}` 结构化引用，schema 层用 `$ref` 校验 | 小（3 天） |

### 7.3 P2 级（清理类，提升可维护性）

| ID | 问题 | 影响 | 修复方向 | 工作量 |
|----|------|------|---------|--------|
| **P2-1** | sfr_groups 与 peripheral 字段冗余 | 双份信息必然失同步 | 移除 sfr_groups，查询时按 peripheral 字段过滤 | 极小（半天） |
| **P2-2** | version_history 手工 JSON 列表 | 与 git 重复，date 字段易腐化 | 改用 `git tag` + `CHANGELOG.md`，JSON 仅保留 `ahal_version` | 极小（半天） |
| **P2-3** | completeness 百分比无校验来源 | 手工填写易偏离实际 | CI 自动统计：覆盖率 = 已定义 SFR 数 / 手册 SFR 总数 | 小（1 天） |
| **P2-4** | forum_qa.verified 无验证流程定义 | 布尔值语义不明 | 改为 `{status, method, evidence_url}` 结构化 | 小（1 天） |

### 7.4 优先级矩阵总览

```
影响 ↑
     │  P0-1(SVD缺失)      │
     │  P0-2(rank fusion)  │
     │─────────────────────│
     │  P1-1(声明式生成)    │  P2-1(sfr_groups冗余)
     │  P1-2(schema标准)    │  P2-2(version_history)
     │  P1-3(错误模型)      │  P2-3(completeness自动化)
     │  P1-4(强类型引用)    │  P2-4(verified流程)
     │─────────────────────│
     └─────────────────────┴──→ 工作量
        中(1-2周)            极小(半天)
```

**建议执行顺序**：P0-2 → P2-1/P2-2/P2-3/P2-4（清理项可并行）→ P0-1 → P1-2/P1-3/P1-4 → P1-1

- P0-2 先做：工作量小，立即提升 LLM 上下文质量。
- P2 清理项并行做：风险低，扫清冗余。
- P0-1 居中：需调研 STC8H SVD 可行性，但价值最大。
- P1 工程化项最后做：在 P0 落地后，schema 形态稳定时再统一升级。

## 八、一句话结论

该协议在"A-HAL + AI 原生 API 契约"上**真创新**（无业界先例，arxiv 论文实证支撑），在"寄存器描述"上**重复造轮子**（无视 CMSIS-SVD 十余年生态），在"混合检索"上**思路对但工程化欠成熟**（未用 RRF/成熟框架）。改进优先级：**P0 引入 SVD 映射 → P0 给 hybrid_search 加 RRF 融合 → P1 补声明式生成链路与标准 schema → P2 清理冗余字段**。

## 九、附录：业界对照速查表

| 维度 | 该协议 | 业界对标 | 差距/定位 |
|------|--------|---------|-----------|
| 寄存器描述 | `registers.json`（手写 JSON） | CMSIS-SVD（XML 标准 + 厂商库 + svd2rust） | **重复造轮子，生态缺失** |
| API Schema | `ahal_api.json`（手写 + 事后 lint） | TF `REGISTER_OP` / Protobuf（声明式 + 生成 + 校验） | **方向对，工程化弱** |
| API 契约元数据 | preconditions/postconditions/side_effects/resource_conflict | TF op shape inference / PyTorch autograd 元数据 | **领先**（面向 AI 代码生成场景） |
| 混合检索 | 精确查表 + 向量检索字段拼接 | LangChain `EnsembleRetriever` + RRF 融合 | **思路对，融合算法缺失** |
| AI 硬件抽象层 | A-HAL（语义化、约束 AI 边界） | 业界空白（TinyML 论文仅 prompt 注入） | **真创新** |
| Schema 标准 | 自造私有 `$schema` URL | JSON Schema 2020-12 / OpenAPI 3.1 | **生态断裂** |
| 版本管理 | 手工 `version_history` JSON | git tag + CHANGELOG.md | **冗余** |
| 错误模型 | 字符串列表 | 结构化错误码 + 严重级别（如 errno） | **欠设计** |
