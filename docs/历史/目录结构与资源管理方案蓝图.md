## 一、设计原则

### 1.1 A区/B区分层

| 区域 | 位置 | 内容 | 分发方式 |
|------|------|------|----------|
| **A区**（仓库区） | `c:\MyLab\MCU\`（git 跟踪） | 纯文本：Python 代码、板定义、知识库、清单索引、测试套件 | pip 随包发布 |
| **B区**（用户区） | `~/.firmforge/`（按需下载） | 二进制/SDK 源码/第三方库 | CLI 按需拉取 |

**核心逻辑**：A区只存放人类可维护的纯文本资源，不包含大型二进制或第三方SDK源码；B区通过版本化清单（manifest）按需下载，实现"仓库轻量、运行时不缺"。

### 1.2 三层库分级（L1/L2/L3）

| 级别 | 说明 | 典型内容 | 存放位置 |
|------|------|----------|----------|
| **L1** | 核心捆绑库 | SPI、Wire、SD、EEPROM 等 MCU 核心通用库 | B区 `packages/`（随 core 包下发） |
| **L2** | 厂商 HAL/驱动 | CMSIS、HAL_Driver、BSP 等 | B区 `packages/`（随厂商包下发） |
| **L3** | 第三方社区库 | Adafruit Sensor、u8g2、FreeRTOS 等 | B区 `libraries/`（按清单解析下载） |

### 1.3 两类示例（E1/E2）

| 类型 | 说明 | 存放逻辑 |
|------|------|----------|
| **E1：库自带示例** | L1/L3 库自带的 example 目录 | 随库保留，不做分离 |
| **E2：厂商独立示例集** | Arduino 内置示例、STM32Cube 示例包等 | A区 `tests/suite/` 作为 board-agnostic 一致性测试套件 |

E2 示例的核心定位：**厂商示例一致性测试套件**（Compatibility Test Suite），而非"语料库"。它是 FirmForge 编译/上传链路正确性的基准验证数据，board-agnostic（不绑定具体板卡），可跨多板卡批量回归。

## 三、关键资源的三处落点（Toolchains）

Toolchains 信息分布在三个位置，各司其职：

| 位置 | 路径 | 内容 | 用途 |
|------|------|------|------|
| **清单定义** | `vendor/manifests/tools/avr_gcc.yaml` | 版本号、各平台下载 URL、SHA256、解压路径模板 | 下载规格（Speccification） |
| **版本引脚** | `firmforge/infrastructure/platform_config.yaml` | `toolchains.avr_gcc: "7.3.0-atmel3.6.1-arduino5"` | 运行时确定使用哪个版本 |
| **二进制实体** | `~/.firmforge/toolchains/avr-gcc/7.3.0-atmel3.6.1-arduino5/` | 实际可执行文件（avr-gcc.exe 等） | 编译/链接/烧录执行 |

**运行时流程**：
1. 读取 `platform_config.yaml` 获取所需版本
2. 检查 `~/.firmforge/toolchains/` 本地是否已缓存
3. 若未缓存，读取 `vendor/manifests/tools/avr_gcc.yaml` 获取下载地址
4. 下载、校验、解压到 B区

同样，`platform_config.yaml` 中的 `packages_root` 指向 `~/.firmforge/packages/`（此前 `arduino_avr_core` 被错误置于 toolchains 分组下，应迁移到 packages 分组）。

## 四、运行时数据流

```
用户执行: ff build --board arduino_328p --sketch my_app/

1. 读取 boards/arduino_328p/board.yaml
   → 确定 MCU: ATmega328P, 厂商: arduino, 架构: avr

2. 读取 vendor/manifests/core/arduino_avr_core.yaml
   → 确定 core 版本, 下载 URL → 检查 B区 packages/ 缓存

3. 读取 vendor/manifests/tools/avr_gcc.yaml
   → 确定工具链版本 → 检查 B区 toolchains/ 缓存

4. 解析 sketch 依赖 → vendor/manifests 中查 L3 库
   → 下载到 B区 libraries/（若未缓存）

5. 编译: AVR-GCC (B区) + Core (B区) + Libraries (B区)
   → 产物输出到 B区 cache/build/

6. 读取 vendor/manifests/tools/avrdude.yaml
   → 烧录工具路径 → 执行烧录
```

## 五、测试套件设计（E2）

### 5.1 `tests/suite/arduino/compatibility.yaml` 示例

```yaml
name: "Arduino AVR Built-in Examples"
source:
  manifest: "vendor/manifests/examples/arduino_avr_examples.yaml"
board_agnostic: true
supported_boards:
  - arduino_328p
  - arduino_mega2560
  - arduino_leonardo

test_cases:
  - sketch: "01.Basics/Blink"
    expected: compile_pass
  - sketch: "02.Digital/BlinkWithoutDelay"
    expected: compile_pass
  - sketch: "03.Analog/AnalogInput"
    expected: compile_pass
  # ... 更多示例

regression:
  enabled: false                    # 暂不启用比特级回归
  tolerance: "bytecode_diff < 5%"   # 未来启用时的容忍度
```

### 5.2 运行方式

```bash
ff test --suite tests/suite/arduino/compatibility.yaml
# → 对所有 supported_boards 批量编译所有 test_cases
# → 输出通过率矩阵
```

## 六、设计决策记录

| 决策 | 理由 |
|------|------|
| 厂商 SDK 不放 git | SDK 体积大（STM32Cube 可达数百 MB）、版本多，git 跟踪无意义且拖垮仓库 |
| 厂商示例不放 boards | 示例是 board-agnostic 的，绑定到板卡目录违反逻辑；boards 仅存放自写的板卡专属应用 |
| E2 示例命名为"一致性测试套件" | FirmForge 是工具链，不是 Agent；"语料库"用语不当，"测试套件"准确反映用途 |
| vendor/manifests 是真相源 | 所有版本信息集中于此，CLI 和 CI 均从 manifest 读取，杜绝版本散落 |
| vendor/.cache/ 在开发期可用 | 避免开发者每次 clean 后重下载 SDK，但此目录 gitignored，不影响分发 |
| tools 清单与二进制分离 | 清单（A区）定义"是什么"，二进制（B区）存放"在哪"，职责清晰 |
| platform_config.yaml 含 packages_root | 将 packages 与 toolchains 正确分离，前者是源码包，后者是二进制工具 |
