## 一、设计目标

当前 MCU 厂商提供的芯片开发资源（数据手册、库函数、社区示例）均面向人类工程师设计，采用 PDF/CHM/ZIP 等人类友好格式。本协议定义将这些资源标准化转换为**AI 原生知识格式**的规范，形成三大知识库，使 AI Agent 能够准确理解硬件、高效检索知识、产出低耦合高内聚且稳健可交付的工程代码。

### 设计原则

| 原则 | 说明 |
|------|------|
| **结构化优先** | 表格、寄存器、API 签名等精确信息用 JSON Schema 严格定义，不依赖向量检索 |
| **语义化标注** | 每个数据条目附带使用场景标签、前置条件、副作用等机器学习可消费的元数据 |
| **可验证性** | 寄存器地址可对芯片数据手册交叉验证，AHL 签名可对实际头文件 lint |
| **增量更新** | 新增外设/API/社区内容不触发全量重建，支持按条目 CRUD |
| **来源追溯** | 每条知识记录源文档、版本、提取时间，支持追踪和审计 |

### AHL 设计原则 v1.1（5 补丁版本）

源自 `AHL设计原则-评价报告.md`，作为 AHL 代码知识库的设计准绳：

| # | 原则 | 说明 |
|---|------|------|
| 1 | **三层防护** | 编译期能挡的不留运行时，运行时挡不了的交给 HIL，HIL 挡不了的交给人工 review。C 无 trait/所有权，编译期防护天然弱于 Rust，须与项目 HIL 三层架构协同 |
| 2 | **AI 难以犯错** | API 应让 LLM 忘记参数时在编译期或生成期报错，而非烧录后炸芯片 |
| 3 | **RAG 友好** | API 命名直观 + `usage_examples` 充实（每 API ≥3 个示例），与类型安全同等重要。Arduino API 反例佐证：无类型安全但 AI 成功率极高（语料海量+命名直观） |
| 4 | **安全分级** | 配置类 API `safety_level: strict`（强编译期检查 + 运行时 assert 兜底），热路径 API `safety_level: fast_path`（允许 `errors.behavior: no_op` 以省 cycles） |
| 5 | **编译期非唯一** | 当编译期防护与性能/RAG 友好冲突时，按 API 分类决策。Arduino 的 RAG 成功证明：API 直观+示例丰富可与类型安全同等重要 |
| 6 | **变长参数安全** | 批量调用用哨兵宏 `AHAL_*_END` 替代 count 参数，避免 count 与数组长度不一致的运行时越界风险 |

**业界定位**：AHL 是 Arduino（RAG 友好）+ Rust embedded-hal（类型安全）+ OpenAI Function Calling（schema 约束）的**折中**，非 Rust 极端。

**检索策略**：
```python
# 精确查表 — 不经过向量化（注：不再使用 sfr_groups，直接按 peripheral 字段过滤）
def query_register(chip: str, sfr_name: str) -> RegisterDef:
    return registers[chip][sfr_name]

def query_registers_by_peripheral(chip: str, peripheral: str) -> list[RegisterDef]:
    return [r for r in registers[chip].values() if r.peripheral == peripheral]
```

**AHL 版本管理**：语义版本号 `MAJOR.MINOR.PATCH` 记录在 `ahl_version` 字段。版本历史使用 `git tag` + `CHANGELOG.md` 标准实践，JSON 中不再维护重复的 `version_history`。

**变长参数安全模式（补丁4）**：

批量调用 API 必须使用哨兵宏替代 `count` 参数，避免 count 与数组长度不一致的运行时越界风险（C 无数组长度推断）：

```c
// ahl/{chip}/gpio.h
#define AHAL_PIN_END  0xFF
#define AHAL_PIN_CFG_END { .pin = AHAL_PIN_END, .mode = 0 }

typedef struct {
    uint8_t pin;
    uint8_t mode;
} ahl_pin_cfg_t;

/// @agent_api
/// @brief 批量设置引脚模式（哨兵宏模式，无需 count 参数）
/// @safety_level strict
/// @precondition cfgs 数组以 AHAL_PIN_CFG_END 哨兵结尾
/// @side_effect 修改各引脚对应的 PxM0/PxM1 寄存器
void ahl_gpio_set_mode_batch(const ahl_pin_cfg_t* cfgs);
```

使用示例（AI 生成）：

```c
ahl_pin_cfg_t pins[] = {
    {PIN_P00, AHAL_GPIO_MODE_PUSHPULL},
    {PIN_P01, AHAL_GPIO_MODE_PUSHPULL},
    {PIN_P03, AHAL_GPIO_MODE_INPUT},
    AHAL_PIN_CFG_END  // 哨兵，命名直观，AI 不易遗忘
};
ahl_gpio_set_mode_batch(pins);  // 内部检测哨兵结束，无需 count
```

**RAG 友好性要求（补丁3）**：

| 要求 | 说明 |
|------|------|
| 命名规范 | `ahl_<module>_<action>_<modifier>`（如 `ahl_uart_init_blocking` 而非 `ahl_uinit`），避免缩写以提高 RAG 检索命中率 |
| usage_examples 数量 | 每个 AHL API 至少 3 个 usage_examples，覆盖常见场景，纳入 `meta.json.completeness` 指标 |
| patterns 覆盖率 | 常见任务（blink/echo/adc_sample/pwm_control）必须有对应 pattern，纳入质量门禁 |
| 语义清晰 | API 命名应让 RAG 检索"gpio set mode"能命中 `ahl_gpio_set_mode`，而非依赖模糊匹配 |

**STM32 AHL 特殊价值**：STM32 HAL 的隐式 RCC 时钟使能、三段式 Init-Use 是 AI 重灾区（AHL 评价报告"AI 友好度"4.7/10）。STM32 AHL 必须封装这些隐式前提——`ahl_gpio_set_mode` 内部自动调用 `__HAL_RCC_GPIOx_CLK_ENABLE()`，AI 无需手动开时钟。这是 AHL 对 STM32 的最大增值。

生成的代码在文件头注释中标注：
```c

// Target: STC8H8K64U
// Requires: ahl-stc8h8k64u >= 1.0.0
// Task: GPIO PA0 toggle every 500ms
```

### 4.2 usage_examples/ — 使用示例

示例代码附带结构化元数据用于 RAG 检索：

 * @example gpio_toggle
 * @module gpio
 * @chip STC8H8K64U
 * @brief 使 PA0（P0.0）引脚以 500ms 周期翻转
 * @ahl_requires 1.0.0
 * @peripherals [GPIO, Timer]
 * @difficulty simple
 * @tags [gpio, toggle, timer, blink, led]
 */
#include "ahl/stc8h8k64u/gpio.h"
#include "ahl/stc8h8k64u/timer.h"

void main(void) {
    ahl_gpio_set_mode(PIN_P00, AHAL_GPIO_MODE_PUSHPULL);
    while (1) {
        ahl_gpio_write(PIN_P00, AHAL_GPIO_HIGH);
        ahl_delay_ms(500);
        ahl_gpio_write(PIN_P00, AHAL_GPIO_LOW);
        ahl_delay_ms(500);
    }
}

## 六、知识库统一查询接口

### 6.1 Python 接口协议

```python
from dataclasses import dataclass
from typing import Optional, Protocol
from pathlib import Path

# ─── 数据模型 ───

@dataclass
class RegisterDef:
    name: str
    address: str
    fields: list[dict]
    access: str
    reset_value: str

@dataclass
class AHALAPIDef:
    name: str
    signature: str
    parameters: list[dict]
    preconditions: list[str]
    side_effects: list[str]

@dataclass
class SearchHit:
    content: str
    source: str           # 来源库：doc_kb | ahl_kb | community_kb
    score: float
    metadata: dict

@dataclass
class ScoredHit:
    """RRF 融合后的统一检索结果。精确查表和向量检索结果经 RRF 排序后统一为此格式。"""
    content: str
    source: str          # doc_kb | ahl_kb | community_kb
    score: float         # RRF 融合后的统一分数（0.0 ~ 1.0）
    metadata: dict
    hit_type: str        # register | api | pattern | doc | community

# ─── 查询接口 ───

class KnowledgeBase(Protocol):
    """三大知识库的统一查询接口"""

    # ── 结构化精确查询（不经 RAG，直接 JSON 查表）──

    def query_register(self, chip: str, sfr_name: str) -> Optional[RegisterDef]:
        """精确查询单个寄存器定义。示例：query_register('stc8h8k64u', 'SCON')"""
        ...

    def query_registers_by_peripheral(self, chip: str, peripheral: str) -> list[RegisterDef]:
        """查询某外设的所有寄存器。示例：query_registers_by_peripheral('stc8h8k64u', 'UART')"""
        ...

    def query_ahl_api(self, chip: str, func_name: str) -> Optional[AHALAPIDef]:
        """精确查询 AHL API 定义。示例：query_ahl_api('stc8h8k64u', 'ahl_uart_init')"""
        ...

    def query_ahl_module(self, chip: str, module: str) -> list[AHALAPIDef]:
        """查询某模块的所有 AHL API。示例：query_ahl_module('stc8h8k64u', 'uart')"""
        ...

    def query_pins(self, chip: str, pin_name: str = None) -> list[dict]:
        """查询引脚定义。pin_name 为空时返回全部"""
        ...

    # ── 向量语义查询（经 ChromaDB 检索）──

    def search_docs(self, chip: str, query: str, top_k: int = 5) -> list[SearchHit]:
        """语义搜索外设文档片段"""
        ...

    def search_patterns(self, chip: str, task_desc: str, top_k: int = 3) -> list[SearchHit]:
        """语义搜索常见任务模式"""
        ...

    def search_community(self, chip: str, question: str, top_k: int = 3) -> list[SearchHit]:
        """语义搜索社区问答和已知问题"""
        ...

    # ── 联合检索（代码生成核心调用）──

    def hybrid_search(self, chip: str, task: str, top_k: int = 15) -> list[ScoredHit]:
        """
        RRF 融合检索：从 TaskPlanner 解析出的外设类型和任务描述中，
        同时进行结构化查表和向量语义检索，用 Reciprocal Rank Fusion 统一排序。
        
        RRF 公式: score(doc) = Σ 1/(k + rank_i(doc))   k 通常取 60
        
        返回: 按 RRF score 降序排列的 ScoredHit 列表，可直接送入 LLM prompt
        """
        ...

    # ── 知识库维护 ──

    def import_doc_kb(self, chip: str, source_path: Path) -> None:
        """从数据手册（MCP查询结果/PDF解析结果）导入文档知识库"""
        ...

    def import_ahl_kb(self, chip: str, ahl_header_dir: Path) -> None:
        """从 AHL 头文件注释中提取并导入 API 知识库"""
        ...

    def rebuild_index(self, chip: str) -> None:
        """重建 ChromaDB 向量索引（新数据导入后调用）"""
        ...
```

### 6.2 检索策略：代码生成流程

```
CodeGenerator 收到任务: "用 UART1 以 115200 波特率回显接收数据"

Step 1: TaskPlanner 解析 → chip=stc8h8k64u, peripheral=UART, mode=echo

Step 2: 精确查表 (JSON)
  ├─ query_registers_by_peripheral("stc8h8k64u", "UART")
  │   → [SCON(0x98), SBUF(0x99), AUXR(0x8E), PCON(0x87)]
  ├─ query_ahl_module("stc8h8k64u", "uart")
  │   → [ahl_uart_init, ahl_uart_send, ahl_uart_read]
  └─ query_pins("stc8h8k64u", "P3.0")
      → {pin:1, primary:GPIO, alt:UART_RxD}

Step 3: 向量语义检索 (ChromaDB)
  ├─ search_docs("ucloud uart echo 115200") → UART模式1配置流程
  ├─ search_patterns("uart echo receive send") → pattern-uart-echo
  └─ search_community("uart 115200 回显") → qa-2024-001 (波特率配置经验)

Step 4: RRF 融合排序（Reciprocal Rank Fusion, k=60）
  ├─ 精确查表命中（无向量分数 → 赋予原始 rank 参与 RRF）
  ├─ 向量检索命中（各自有 cosine score → 按 rank 参与 RRF）
  ├─ RRF 统一排序 → 去重（同一 SFR 从多源命中时保留最高分）
  └─ Top-K=15 → 送入 LLM prompt

Step 5: LLM 接收 RRF 排序后的 ScoredHit 列表生成代码
  Prompt 中信息已按相关性降序排列，优先消费高分结果
```

## 八、SVD 渐进迁移路径（v2.0 调整：Arduino+STM32 优先）

v2.0 总体规划将首发芯片调整为 Arduino Mega2560 + STM32F103，SVD 策略按芯片分类：

| 芯片 | 架构 | SVD 来源 | 策略 |
|------|------|---------|------|
| **STM32F103** | Cortex-M3 | ST 官方 SVD | 直接下载导入，`svd_to_json.py` 转换为 registers.json |
| **Arduino Mega2560** | AVR (ATmega2560) | 无官方 SVD | 自研 AVR SVD Profile（CPU 填 AVR，vendorExtensions 承载 AVR 特有概念） |
| STC8H8K64U（后期） | 8051 | 无官方 SVD | 自研 STC8H SVD Profile（vendorExtensions 承载位寻址/TA 解锁序列） |

**阶段 A（当前，STM32）**：直接下载 ST 官方 SVD 作为单一真相源，`svd_to_json.py` 自动生成 LLM 友好的 registers.json 扁平视图

**阶段 B（当前，Arduino）**：自研 ATmega2560 AVR SVD Profile，参考 Microchip ATDF 格式，复用 CMSIS-SVD XML 结构

**阶段 C（后期，STC8H）**：编写 `tools/svd_exporter.py`，将 STC8H registers.json 导出为 registers.svd（8051 vendorExtensions 承载位寻址/TA 解锁序列等特有概念）

**阶段 D**：评估 svd2rust 生成 Rust PAC 的可行性（若未来扩展 Rust AHL）

**SVD ↔ registers.json 字段映射**：

| registers.json | SVD XML | 说明 |
|---------------|---------|------|
| `name` | `<name>` | 直接映射 |
| `address` | `<addressOffset>` + `baseAddress` | JSON 值为绝对地址 |
| `access` | `<access>` | `R/W` → `read-write`，`R only` → `read-only` |
| `reset_value` | `<resetValue>` | 直接映射 |
| `fields[].name` | `<field>/<name>` | 直接映射 |
| `fields[].bits` | `<bitRange>` | `[3,2]` → `[3:2]` |
| `fields[].values` | `<enumeratedValues>` | 直接映射 |
| `special/access_sequence` | `<vendorExtensions>` | 8051 特有 |

## 九、格式校验与质量门禁

每个 JSON 文件在导入前需通过 schema 校验（使用 JSON Schema 2020-12 标准验证器）：

```bash
# 校验寄存器定义
python -m mcu_agent.kb.validator memory/doc_kb/stc8h8k64u/registers.json \
  --schema https://json-schema.org/draft/2020-12/schema

# 校验 AHL API 定义（自动提取后调用）
python -m mcu_agent.kb.validator memory/ahl_kb/stc8h8k64u/ahl_api.json

# 交叉一致性检查：AHL API 引用的寄存器是否在 registers.json 中存在
python -m mcu_agent.kb.consistency_check stc8h8k64u

# 自动统计知识库覆盖率
python -m mcu_agent.kb.completeness_check stc8h8k64u
```

质量门禁：
- registers.json 中所有 SFR 地址与官方数据手册交叉校验通过
- ahl_api.json 由 `extract_ahl` 自动从头文件生成，消除手工维护
- consistency_check 识别出的不一致项必须修复或标注为 `known_gap`
- completeness_check 统计数据实时更新 meta.json 的 `completeness` 字段
- 新增外设至少包含 registers + peripherals/*.md + AHL API 三个来源的定义
- **safety_level 校验**：每个 AHL API 必须声明 `safety_level: strict | fast_path`，`fast_path` API 必须有 `errors.behavior: no_op` 说明
- **RAG 友好性校验**：每个 AHL API 至少 3 个 usage_examples，命名符合 `ahl_<module>_<action>_<modifier>` 规范
- **变长参数校验**：批量调用 API 必须使用哨兵宏模式（`AHAL_*_END`），禁止 `count` 参数模式
- **三层防护校验**：`strict` API 必须有 preconditions + side_effects 声明，`fast_path` API 必须在 ai_hint 中说明运行时不检查的原因
